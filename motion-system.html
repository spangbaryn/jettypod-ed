Motion Patterns

1. Entrance Choreography

Elements assemble in sequence on page load. Each item uses --motion-slower (600ms) with stagger delays of --stagger-base (80ms). The assemble keyframe combines opacity + translateY for a "rising into place" effect.

5. Emphasis Transitions

Tab panels and slide indicators use --ease-emphasis with --motion-slow. This curve is weightier, suited for content that demands attention during its movement.

/* Tab panel slide */
.slide-tab-panel {
  transition: opacity var(--motion-slow) var(--ease-emphasis),
              transform var(--motion-slow) var(--ease-emphasis);
}

/* Slide indicator */
.slide-indicator {
  transition: top var(--motion-slow) var(--ease-emphasis),
              height var(--motion-slow) var(--ease-emphasis);
}

6. Reduced Motion

All choreography and reveals are disabled when prefers-reduced-motion: reduce is active. Elements appear immediately with no animation or transition.

/* Respects user preference */
@media (prefers-reduced-motion: reduce) {
  .hero-enter,
  .reveal {
    animation: none;
    transition: none;
    opacity: 1;
    transform: none;
  }
}

Usage Guide

When to use each duration

--motion-fast (150ms)
Button hover, link hover, focus rings, active states, input focus, nav opacity changes. Anything the user's finger/cursor directly triggers.
--motion-normal (250ms)
Fades in/out, state toggles (show/hide), color changes, scroll section opacity, challenge card opacity, rotating text, toast/copied messages.
--motion-slow (400ms)
Tab panel slides, modal entries, triangle image crossfade, OS selector pill, slide indicator movement, hero screenshot fade.
--motion-slower (600ms)
Page load choreography, scroll-triggered reveals, email form entrance. Spatial entrance animations that establish presence.

When to use each easing

--ease-out
Default for everything. Elements arrive quickly and settle gently. Use this unless you have a specific reason not to.
--ease-in-out
Symmetric/looping motion only: rotating text carousel, any animation that cycles. The symmetry matches the cyclical nature.
--ease-spring
Playful overshoot. Currently only used for OS selector pill. Adds personality but can feel chaotic if overused. Max 1-2 uses per page.
--ease-emphasis
Large spatial moves where content replaces other content: tab panels sliding in/out, slide indicators tracking position. The deliberate feel matches the weight of a content change.

Decision Log

Design decisions made during the creation of this motion system, with rationale and alternatives considered.

D1: Four-step duration scale (150/250/400/600ms)
Chosen for clear semantic separation. Each step is roughly 1.6x the previous (close to the golden ratio), creating a natural visual hierarchy. 150ms is the threshold where movement feels "instant but smooth." 600ms is the upper bound before motion feels sluggish.
Alternatives considered: Three-step scale (150/300/500) felt too coarse — no distinction between "standard fade" and "panel slide." Five steps added complexity without clear use cases for the extra tier. Linear scale (100/200/300/400) lacked the perceptual spacing needed.
D2: cubic-bezier(0.16, 1, 0.3, 1) as default easing
This is a refined ease-out that starts fast and decelerates smoothly. It gives elements a sense of arriving with purpose — they snap into position rather than drifting. Matches the "assembled with care" brand principle: things arrive decisively, not lazily.
Alternatives considered: CSS ease-out (0, 0, 0.58, 1) decelerates too gently, making things feel floaty. Material's standard curve (0.4, 0, 0.2, 1) is too subtle for small elements. The chosen curve sits between confident and graceful.
D3: 80ms stagger base for choreography
80ms creates a perceptible but rapid cascade. At 5 items (hero sequence), total stagger span is 400ms — the entire sequence completes within 1 second (600ms animation + 400ms stagger = last item finishes at ~1s). Fast enough to not feel like waiting, slow enough to read as intentional sequence rather than simultaneous pop.
Alternatives considered: 50ms felt simultaneous beyond 3 items. 120ms made 5-item sequences feel slow (720ms span). 100ms was viable but 80ms hit the sweet spot of "noticeable cascade without drag."
D4: translateY(12px) for entrance, translateY(16px) for scroll reveals
Entrance elements (hero) use 12px — subtle enough to not distract from content on first impression. Scroll reveals use 16px — slightly more pronounced since the user is already engaged and scrolling. Both are small enough to feel like "assembling in place" rather than "flying in from somewhere."
Alternatives considered: translateY(20px+) felt like slide-in animations from a UI framework, not "considered assembly." translateY(8px) was too subtle to register on scroll. No translateY (opacity-only) lacked the spatial quality that signals physical assembly. Scale transforms (0.95 → 1) felt more "zoom" than "place."
D5: CSS custom properties over a JS motion library
This is a static site with no build system or framework. CSS custom properties provide the token system natively with zero runtime cost and no dependencies. The motion patterns needed (entrance, fade, slide) are all achievable with CSS alone. JS is only needed for IntersectionObserver triggers.
Alternatives considered: Framer Motion requires React. GSAP adds 30KB+ for capabilities we don't need. Web Animations API would work but adds JS complexity for transitions CSS handles natively. animate.css provides premade animations but not a token system.
D6: Removing all transition: all declarations
Replaced 10 instances with explicit property lists. transition: all is a performance anti-pattern — it forces the browser to watch every property for changes, and it can cause unintended transitions (e.g., layout shifts triggering width/height animations). Explicit properties make intent clear and prevent surprises.
Alternatives considered: Keeping transition: all with will-change hints — rejected because it treats symptoms, not the cause. The effort to enumerate properties is trivial and the benefit in both performance and maintainability is clear.
D7: IntersectionObserver with unobserve for scroll reveals
Elements reveal once and stay visible. No reverse animation on scroll-up. This matches the "assembled" metaphor — once a piece is placed, it stays. Unobserving after reveal also eliminates ongoing observer overhead. Threshold of 0.15 (15% visible) triggers early enough that the animation is visible, not already past.
Alternatives considered: Scroll-linked animations (CSS scroll-timeline) would enable reverse animations but add complexity and lack Safari support. Re-animating on scroll-up (bidirectional reveals) would undermine the "assembled" metaphor. Larger threshold (0.3+) would cause elements to pop in too late, especially on mobile.
D8: Keeping the spring easing for OS selector pill
The bouncy overshoot on the OS selector pill is a deliberate moment of personality. It signals "this is interactive and fun" in a UI that's otherwise restrained. Limiting spring easing to this one element prevents it from feeling chaotic while still injecting a moment of delight.
Alternatives considered: Replacing with --ease-out for full consistency — rejected because it would flatten the only playful moment in the UI. Using spring on more elements — rejected because it would dilute the effect and make the page feel bouncy rather than precise. Removing the pill animation entirely — rejected because the sliding pill is satisfying UX feedback for OS selection.
D9: Email form entrance uses assemble keyframe with 150ms delay
When the user clicks "Join the Waitlist," buttons exit immediately (opacity 0 via class toggle), then the form assembles 150ms later. This gap is short enough to feel continuous but long enough to prevent visual collision between the exiting buttons and entering form. The screenshot fades simultaneously via its own CSS transition.
Alternatives considered: Simultaneous crossfade — rejected because buttons and form overlap spatially, creating visual noise. Longer delay (300ms+) — felt sluggish and broke the "responsive UI" expectation. No delay — form appeared before buttons finished hiding, looking glitchy.
D10: Removing inline transition styles from section-renderer.js
The JS renderers were setting transition: opacity 0.3s ease-out inline, duplicating what the CSS classes (.section-background, .section-content) already provide. Removed the inline styles so transitions are governed solely by the stylesheet, making them token-driven and centrally maintainable.
Alternatives considered: Keeping inline styles as "safety net" in case CSS classes change — rejected because dual sources of truth create maintenance confusion. Reading CSS custom properties via getComputedStyle — rejected as over-engineered for values that the stylesheet already handles.
